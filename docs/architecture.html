벡터 저장소 3종 아키텍처

OpenShift AI 3.4의 Llama Stack이 pgvector / FAISS / Qdrant 세 벡터 저장소와 Qwen2.5-3B(vLLM) 추론을 어떻게 같은 API 뒤에서 갈아끼우는지 보여주는 다이어그램입니다. 브라우저(챗 UI)와 CLI(데모 스크립트) 두 클라이언트가 완전히 동일한 호출로 접근하고, 각 트랙은 검색된 문서를 근거로 실제 답변까지 생성합니다.

Llama Stack이 필요한 이유

애플리케이션 코드(webapp/app.py, scripts/*.py)는 pgvector·FAISS· Qdrant·vLLM을 직접 모릅니다 — Llama Stack 하나가 그 넷을 vector_io / inference provider로 숨기고, 코드는 vector_stores.search(...)와 chat.completions.create(...) 두 호출만 압니다. 즉 애플리케이션 코드는 Llama Stack으로 백엔드를 추상화할 수 있습니다. 그리고 이 데모의 목적 자체가 "OpenShift AI 3.4가 여러 벡터 저장소를 동등하게 지원하는가"이므로, Llama Stack은 이 데모가 고른 도구가 아니라 검증 대상 그 자체입니다.

요청 흐름 — 브라우저에서 질의 하나를 입력했을 때

  1. chat-ui가 /api/search로 질의를 받는다.
  2. 같은 함수가 pgvector / FAISS / Qdrant 세 서비스(모두 같은 Llama Stack 서버)에 동시에 vector_stores.search(search_mode=...)를 호출한다 — 코드는 세 트랙 모두 동일하다.
  3. 각 트랙은 자기 백엔드에서 검색한다: pgvector는 SQL로, FAISS는 파드 내부 인덱스에서, Qdrant는 자신의 엔진에서(요청한 모드가 vector면 벡터만, keyword/hybrid면 어휘 점수까지 결합).
  4. chat-ui가 검색된 상위 문서를 프롬프트에 넣어, 이번엔 각 트랙의 Llama Stack 파드에 chat.completions.create(...)를 호출한다 — qwen-vllm에 직접 붙는 게 아니라 이것도 Llama Stack API다. 파드가 이 요청을 받아 내부적으로 공용 qwen-vllm에 전달해 실제 답변을 만들어 돌려준다(demo-runner Job은 이 호출을 하지 않는다 — CLI 데모는 검색까지만 확인한다).
  5. 검색 결과 + 생성된 답변을 카드 3개로 모아 브라우저에 반환한다 — Qdrant 카드는 vector/keyword/hybrid 탭을 눌러 같은 데이터를 다른 모드로 다시 볼 수 있다.
